# pilot-client

React 19 SPA for Pursuit's learning management platform. Serves builders (learners), staff, admins, volunteers, and applicants with role-based access control.

## Quick Reference

- **Entry**: `src/main.jsx` → `src/App.jsx` (routes + providers)
- **Build**: Vite 6 — `npm run dev` (port 5173), `npm run build`
- **Test**: `npm test` (Vitest), `npm run test:ui`, `npm run test:coverage`
- **Deploy**: Netlify (`netlify.toml`); Node 20, npm 10.9.0
- **Partner repo**: `../test-pilot-server` (Express backend on port 7001)

## Auth Flow

1. Login → `POST /api/unified-auth/login` → receives `{ user, token, redirectTo, userType }`
2. Token + user stored in localStorage
3. Permissions fetched from `GET /api/permissions/my-permissions` → cached in authStore
4. All API calls include `Authorization: Bearer <token>` header
5. Global error handler detects 401/403 → `ExpiredTokenModal` → redirect to login

**Roles**: `admin` (wildcard '*'), `staff`, `builder`, `volunteer`, `workshop_participant`, `enterprise_builder`, `enterprise_admin`, `candidate`, `applicant`

## Permission System

`usePermissions()` hook — hybrid DB-sourced + hardcoded fallback:
- `hasPermission(key)`, `canAccessPage(page)`, `canUseFeature(feature)`
- Admin bypasses all checks
- Permissions drive nav visibility and route guards (`components/RouteGuards/`)
- Defined in `constants/permissions.js` with `DEFAULT_ROLE_PERMISSIONS` fallback

**Admin-only pages (2026-07-07):** `page:external_cohorts` and `page:coach` (the merge of the former `page:coach_observability` + `page:coach_evals`) are admin-only — intentionally NOT staff defaults in either `DEFAULT_ROLE_PERMISSIONS` or the server `role_permissions` table (server migration `20260707_admin_only_external_cohorts_coach.sql`). Staff see those pages only via an explicit grant in Permission Management. The `Layout.jsx` Admin dropdown is built for any staff/admin with per-item `canView*` flags and self-hides when empty — the old `hasAnyAdminPagePermission` whitelist was removed because it silently hid granted-but-unlisted items (External Cohorts, Coach) from staff. `NavDropdown.jsx`'s collapsed vertical page-title overlay reserves `min-h-[176px]` so a one-item dropdown (e.g. staff granted only External Cohorts) doesn't overlap the trigger icon. **ExternalCohortsDashboard is fully covered by `page:external_cohorts` (2026-07-16):** every remaining action on the page hits `/api/external-cohorts/*` endpoints that accept that one permission, so any grantee (any role) gets full functionality — the "Upload Curriculum" action (the page's only call into `/api/curriculum/bulk-upload`, gated by the separate `feature:edit_curriculum`) was removed; curriculum upload happens via the Content Management page.

## State Management (Zustand)

Auth and nav state live in Zustand stores (`src/stores/`), not React Context. There are no Context providers to wrap.

### authStore (`src/stores/authStore.js`)

```js
import useAuthStore from '@/stores/authStore';

// Reading state — use selectors for optimal re-renders
const user = useAuthStore((s) => s.user);
const token = useAuthStore((s) => s.token);
const permissions = useAuthStore((s) => s.permissions);
const isAuthenticated = useAuthStore((s) => s.isAuthenticated);

// Multiple values — single selector returning an object
const { user, token } = useAuthStore((s) => ({ user: s.user, token: s.token }));

// Actions
const login = useAuthStore((s) => s.login);       // (credentials) → API call, sets user+token+permissions
const signup = useAuthStore((s) => s.signup);      // (userData) → API call, sets user+token
const logout = useAuthStore((s) => s.logout);      // () → clears state + localStorage
const updateUser = useAuthStore((s) => s.updateUser); // (fields) → merges into user object
const setAuthState = useAuthStore((s) => s.setAuthState); // (stateObj) → bulk update
const refreshPermissions = useAuthStore((s) => s.refreshPermissions); // () → re-fetches from API
```

**Persistence**: `user` and `token` auto-persist to localStorage via Zustand `persist` middleware. On page reload, state rehydrates automatically and `refreshPermissions` runs to re-fetch permissions from the server.

### navStore (`src/stores/navStore.js`)

```js
import useNavStore from '@/stores/navStore';

const isSecondaryNavPage = useNavStore((s) => s.isSecondaryNavPage);
const setIsSecondaryNavPage = useNavStore((s) => s.setIsSecondaryNavPage);
```

### Testing with Zustand stores

Do NOT wrap components in providers. Set state directly before each test:

```js
import useAuthStore from '@/stores/authStore';

beforeEach(() => {
  useAuthStore.setState({
    user: { id: 1, role: 'builder', firstName: 'Test' },
    token: 'test-token',
    permissions: [],
    isAuthenticated: true,
  });
});

afterEach(() => {
  useAuthStore.setState(useAuthStore.getInitialState());
});
```

**Builder Snapshot defect sweep (2026-07-28).** Five fixes, all found on one real builder (Dennys Antunish, 21 graded tasks), each of which had been making builders look weaker than the data said or dropping the data entirely. Regression tests for all five in `__tests__/BuilderSnapshot.test.jsx`; each was verified to fail against the pre-fix components.
- **The hero KPI leads with the Dreyfus STAGE, not a fraction.** "Avg Proficiency 1.6 / 5" reads as 32% — a failing grade — when Advanced Beginner four weeks into L1 is on track. It is now "Proficiency Stage · Advanced Beginner" with the mean demoted to the hint (`Dreyfus 1.9 of 5 · 9 skills assessed`). Dreyfus is an ordinal ladder; **never render it as a fraction or a percentage.**
- **`overall_score` is never displayed.** `BuilderSnapshotTimeline`'s `ScoreChip` rendered the raw derived score and coloured it amber below 70, so all 21 of Dennys's tasks — every one `passed: true`, scoring 20–60 — read as near-failures. Replaced by `OutcomeChip` (✓ Passed / ✗ Not passed). There is **no 0-100 pass bar in the engine**; pass is window-relative. CoachRuns went Dreyfus-first for this reason on 2026-07-07 and the snapshot had never followed.
- **The timeline summary was unreadable.** It is `truncate`d in the collapsed row and the expanded view rendered only went-well / to-improve, so the sentence could never be finished no matter what was clicked. `ExpandedDetail` now repeats the full summary, and **renders `trajectory_note`** ("Pattern over time") — the grader's cross-session read, captured on every entry and previously displayed nowhere.
- **Task titles.** Performance entries carry only `task_id`; the endpoint already returns `recent_apply_outcomes` with a resolved `task_title`, which the client never read. `BuilderSnapshotTimeline` takes an `applyOutcomes` prop and indexes titles by `task_id`.
- **`BuilderSnapshotAchievements` (now "Strongest Skills") was doubly broken.** Its "Most recent" block read `latest.summary`; evidence objects have no `summary` key (it is `evidence`), so the block had **never rendered for any builder**. And it ranked by evidence COUNT — which measures how often a skill was tagged, not how well it was done — so Dennys's #1 "Mastery" was `use-ai-coding-tools`, his weakest skill, several of whose signals read "No direct AI coding tool usage was observed." Ranking is now level → confidence → count, the crest shows the Dreyfus stage, and onboarding priors (`task_id: null`) are excluded from the count. It takes a `skillProficiency` prop. Note `competencies.by_skill` values are the evidence **array** in prod; the component tolerates the `{ evidence: [...] }` wrapper too.
- **`TEACHING_METHOD_LABEL` in `BuilderSnapshotStoryGrid` had 3 of the 6 enum values**, so `experiential` / `inquiry_based` / `problem_based` rendered as raw lowercase slugs ("Prefers experiential"). All six are mapped, plus the retired `demonstration` → Example-Based alias the server also applies at read time.

**Readiness panel — `components/BuilderSnapshotReadiness.jsx` (2026-08-03).** The hero's KPI strip is **gone** (`heroKpis` deleted; `BuilderSnapshotHero` still supports a `kpis` prop and self-hides on an empty array). It headlined "Avg Proficiency X / 5" plus raw counts, and was replaced wholesale by this panel, which answers the question the page exists for: *is this builder going to keep doing well?*

**Why there is no single number, and no composite score.** `/5` is not a reachable denominator in a first course — Dreyfus 4–5 maps to the taxonomy's `adaptation` tier, whose definitions are team-scoped ("enforces a branching strategy **for a team**", "reviews others' PRs"). The mean also averaged ordinal stages across skills with 1–10 observations and confidence 0.2–1.0 weighted equally, *including* skills the course doesn't teach (13% of L1-July assessments are tagged `learnedIn` L2/L3, where being early is **ahead**). And a level alone actively misleads: across 76 L1-July builders, **18 sit below the cohort median but are improving, 9 sit above it but are declining, and 10 stopped being graded entirely (3 of those above median) — 49% would be misread.** So four signals render **separately**, each showing its own arithmetic: **Skill stages** (level histogram + peer percentile + the course's reachable band + `ahead:`/`earlier course:` chips), **Direction** (improved/held/declined vs the builder's *own* prior), **Coaching needed** (learn-cap hit rate against the cohort median), **Engagement** (sessions + recency, so a builder who has gone quiet is visible). Deliberately **no readiness score and no pass threshold** — Pursuit's real L1 bars are participation (>80% attendance, demo day), no skill-level exit bar has been validated, and inventing one would turn a made-up number into a gate. Same call `CohortInsights` made.

Data comes from the `readiness` block on `GET /api/admin/builder-profiles/:userId` (server `queries/builderReadiness.js`); it is `null` for a builder with no active enrollment and the panel then **self-hides** rather than inventing peers. Tier/band labels come from `skill_proficiency_scale.tiers` + `.courseBands` via `data.skillProficiency.scale` on the **existing** `/v2-coach-engine` bundle fetch (no new request) — the mapping is DB data, not hardcoded.

**Chart conventions (validated, don't casually change).** Level distribution is **sequential** — the same grey→indigo `LEVEL_RAMP` the Skill Profile meters use, so a stage reads identically across the page. Movement is **diverging**: `#0d9488` teal (improved) / `#525252` neutral-600 (held) / `#ea580c` orange (declined). The app's usual emerald↔rose was **rejected — ΔE 5.8 in deuteranopia**, i.e. a colourblind reader cannot separate improved from declined at all; teal↔orange measures 13.8 protan / 34.5 tritan. The midpoint is deliberately near-zero chroma (a diverging midpoint must be neutral) and is separated from teal by **lightness**, which is why it's neutral-600 and not slate-500 (slate's blue-green cast put it at normal-vision ΔE 11 against teal — a hard fail). Every segment also carries an arrow + count, so movement is never colour-alone. Bars use 2px surface gaps and direct labels on any segment wide enough. Verified rendered at 1440/1024/768/390 — no horizontal overflow at any width.

## AI Chat Truncation & Continue Button

Both `pages/GPT/GPT.jsx` and `pages/Learning/Learning.jsx` consume the SSE `done` event's `finish_reason` field (forwarded by the backend — see `test-pilot-server/CLAUDE.md`). When `finish_reason === 'length'` (OpenRouter/OpenAI) or `'max_tokens'` (Anthropic), the assistant message is marked `truncated: true` in component state and a small **⏵ Continue** button renders directly under the bubble with the caption "Response was cut off." Clicking it submits the literal prompt `"Please continue exactly where you left off, without repeating any prior content."` through the existing send handler — no new API contract, the continuation appears as a normal next assistant turn. If the continuation also truncates, the button reappears on the new bubble; the user stays in control of cost.

- `GPT.jsx`: `sendMessageToExistingThread(overrideContent)` accepts an optional content override; `handleContinueGeneration` calls it with the continuation prompt. The new-thread send path also sets `truncated` on the assistant message, though Continue itself only fires once a thread is active.
- `Learning.jsx`: `handleSendMessage(messageContent, model)` already accepts content directly, so `handleContinueGeneration` just calls it with the continuation prompt + current `selectedModel`.
- Both pages clear the `truncated` flag on prior messages when a new user message is sent, so stale Continue buttons disappear.
- **Model picker (2026-07-09, roster refreshed 2026-07-20)**: the LLM dropdown list is duplicated in `components/AutoExpandTextarea.jsx` (`LLM_MODELS`, used by Learning) and `pages/GPT/GPT.jsx` — keep them in sync. 2026-07-20 roster: Claude Sonnet 5 / Opus 4.8, GPT 5.6 Sol/Terra/Luna, Gemini 3.1 Pro Preview, Grok 4.5, Kimi K3, GLM 5.2, Deepseek V4 Pro (Minimax removed; Fable 5 rejected as too expensive; old threads with retired slugs still resolve server-side). ## Coach / Learning deliverable panel

The V2 Coach APPLY-phase deliverable panel (`src/pages/Learning/components/DeliverablePanel/`) supports file and URL deliverables in addition to image/video/structured/link/document.

- **Per-type routing (2026-07-23)**: `DeliverablePanel.jsx` exports a **pure `resolveDeliverablePanel(task)`** returning one of `structured | video | image | file | link | none`; `getSubmissionComponent` switches on it. The old catch-all "everything else → FlexibleSubmission (generic)" is gone — mapping is an **explicit allowlist**, so `'none'` (the terminal `NoDeliverableConfigured` panel) is reached only by a genuinely unconfigured/unknown `deliverable_type`, never as a silent generic fallback. Routing is unit-tested in `__tests__/resolveDeliverablePanel.test.js`, and each type is verified at the render level (correct panel mounts + submit payload) in `__tests__/DeliverablePanel.test.jsx`.
- **Dedicated per-type panels**: `LinkSubmission` (URL input + preview — link/document/url/presentation), `ImageSubmission` (upload), `FileSubmission` (upload), `StructuredSubmission` (multi-field schema form — used both for `deliverable_schema` tasks AND for `video` via the Loom `loom_url` field). All **on-theme Tailwind** (Pursuit purple `#4242EA`, Proxima, `#F1F1F1`/white rounded inputs). (History: the old router dropped everything non-image/file/video into a generic `FlexibleSubmission`; that was replaced by per-type routing. A detour that (a) split into a generic `SubmissionForm`, (b) added bare `TextSubmission`/`VideoSubmission` panels, and (c) added `text`/`presentation` to the button allowlist was reverted — `TextSubmission.jsx`/`VideoSubmission.jsx` + the dead `DeliverablePanel.css`/`react-icons` were removed, video restored to the Loom `StructuredSubmission`, and text restored to conversation-only.)
- **NoDeliverableConfigured** (`DeliverablePanel/NoDeliverableConfigured.jsx`, new): terminal "No deliverable to submit" state — seeing it means the task's `deliverable_type` is unset/unrecognized and needs attention, not that the UI is guessing.

## Survey interface (builder-facing)

`src/components/SurveyInterface/SurveyInterface.jsx` renders every `feedback_slot` task (weekly survey, L1/L2/L3 finals, end-of-cycle). Questions come from the DB — `GET /api/admin/templates/surveys/by-type/:surveyType` where `surveyType` is the task's `feedback_slot` — with a hardcoded 5-question fallback used only when that fetch fails or 404s. Progress is checkpointed to localStorage under `survey_progress_${taskId}_${surveyType}` (plus `_preview`) on every answer and nav, and cleared on successful submit.

**Template edits can strand builders mid-survey (fixed 2026-07-27).** `survey_templates` is staff-editable, so a template can *shrink* under a builder who already has a saved position in the longer version — and localStorage survives a hard refresh, so it's sticky per browser with no server-side trace. Restoring an out-of-range index made `questions[currentQuestionIndex]` undefined and `currentQuestion.question` threw; **there is no ErrorBoundary in `Learning.jsx` or `App.jsx`, so that throw blanks the entire Learning page**, not just the survey. Three guards now: the exported pure **`clampQuestionIndex(index, questionCount)`** (coerces/floors/caps, `__tests__/clampQuestionIndex.test.js`); the localStorage restore **discards saved progress outright** when its index exceeds the current question list (those answers are keyed to questions that no longer exist, so a clean restart beats a half-restored one) and removes the stale key; and a clamping `useEffect` + a non-throwing render guard catch every other path (e.g. a `surveyType` change swapping in a shorter set while the index persists in component state). Real incident: the `weekly` template was swapped from the 10-question "End of Cycle Survey" to a new 5-question one on 2026-07-01, which blank-screened the 2026-06-30 L2 - June 2026 weekly survey (task 8243) for anyone who'd reached question 6+ — 9 of 45 builders submitted that week. Note survey tasks are excluded from missed-assignment counts server-side (`queries/userProgress.js:761` gates on `should_analyze`/`deliverable_type`/`assessment_id`, and survey tasks have none), so an unsubmitted survey carries no builder-facing penalty.

**NPS question ids are not stable** — the same 2026-07-01 rebuild renamed the NPS question `referral_likelihood` → `nps`, which routed the score into the generic `survey_responses` JSONB and left the dedicated column NULL. The server canonicalizes NPS-shaped answers back into `referral_likelihood` (`utils/npsExtraction.js`); keep NPS question ids NPS-shaped (matching nps/referral/recommend) or the score silently stops flowing. A consequence for analysis: a week whose template changed mid-flight holds rows in **multiple id shapes**, so only NPS is comparable across them.

## Client-Server Contract

This app consumes the REST + SSE API from `../test-pilot-server`:
